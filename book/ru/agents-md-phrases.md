# Фразы для AGENTS.md

Здесь собраны правила для [памяти проекта](agents-md-memory.md), которые помогают агенту принимать решения при выборе реализации. Подбирайте их под проект и добавляйте только те, которые меняют поведение агента в нужную сторону.

Первые пять правил основаны на списке Marcos Hernanz; формулировки про причину ошибки и рефакторинг добавил [Кирилл Мокевнин](https://x.com/mokevnin/status/2083152573679173830). Далее приведены правило из навыка Cloudflare и адаптации инструкций из открытых проектов. В соответствующих разделах даны ссылки на первоисточники.

Выберите из блока правила, которые нужны вашему проекту, и перенесите их в файл памяти. Копировать весь список не нужно.

```markdown
# AGENTS.md
- Do not preserve backward compatibility.
- Choose the simplest implementation that fully meets the current requirements.
- Prefer established, well-maintained libraries over custom implementations.
- Fix the cause, not the symptom.
- Suggest best practices, even if they may require refactoring.
- Prefer retrieval over pre-training.
- Keep changes focused on the requested task.
- Make behavior-changing assumptions explicit.
- Report what you verified and what you could not verify.
```

Правила приведены на английском. При желании переведите их на язык команды. Как объясняет глава [«Память проекта»](agents-md-memory.md), файл _направляет_ поведение агента, но не гарантирует соблюдения правил. Держите список коротким, чтобы он не превратился в [раздутую память](bloated-agents-md.md).

## Do not preserve backward compatibility

_Не тащи обратную совместимость._

Правило разрешает убрать ненужные слои совместимости, когда команда контролирует всех потребителей. Для внешнего API совместимость входит в контракт. Как выбрать между общей правкой и постепенной миграцией, разобрано в [«Рефакторинге»](refactoring.md).

## Choose the simplest implementation that fully meets the current requirements

_Выбирай простейшую реализацию, полностью закрывающую текущие требования._

Правило удерживает агента в рамках текущих требований и требует закрыть весь согласованный сценарий, включая ошибки. Применение к лишним абстракциям разобрано в [«Рефакторинге»](refactoring.md), а выбор устройства решения слишком рано — в [«Преждевременной спецификации»](premature-specification.md).

## Prefer established, well-maintained libraries over custom implementations

_Предпочитай зрелые, поддерживаемые библиотеки самописным реализациям._

Агент может написать собственный парсер дат, который проходит простой пример и ошибается на переходе часового пояса. У зрелой библиотеки такие случаи уже могут быть разобраны и покрыты тестами. Правило побуждает проверить готовые решения и сократить объём кода, который команда будет сопровождать сама.

Перед выбором библиотеки проверьте состояние репозитория, релизы и поддержку нужных сценариев. Заброшенная зависимость может потребовать больше работы, чем собственная реализация.

## Fix the cause, not the symptom

_Найди и исправь причину ошибки._

Столкнувшись с падающим тестом, агент может добавить `try/catch`, после которого симптом исчезнет. Если ошибка возникла из-за неожиданного `null`, такое исправление оставит источник некорректного значения на месте. Правило требует выяснить, откуда пришёл `null` и какой контракт нарушен.

Правило можно сочетать с [рефлексией](reflection.md). Перед правкой агент объясняет причину сбоя, и вы проверяете, устраняет ли предложенное изменение эту причину.

## Suggest best practices, even if they may require refactoring

_Предлагай лучшие практики, даже если они могут потребовать рефакторинга._

Правило разрешает агенту предложить структурное улучшение и объяснить пользу для задачи. Вы выбираете объём работы; предложение само по себе не разрешает правки. Как оценить и проверить улучшение, разобрано в [«Рефакторинге»](refactoring.md).

## Prefer retrieval over pre-training

_Предпочитайте проверку источников знаниям модели из обучения._

Это дословная формулировка из [навыка Cloudflare Agents SDK](https://github.com/cloudflare/skills/blob/6eb6c781aa9b6438e0c7307bd102788a75fe1a6d/skills/agents-sdk/SKILL.md#L8). Агент может помнить метод SDK, который уже переименовали, или ограничение сервиса, которое изменилось. Правило побуждает его открыть документацию или исходный код перед тем, как выбирать API и ссылаться на лимиты.

Проверять нужно версию, которую использует проект. В [общем навыке Cloudflare](https://github.com/cloudflare/skills/blob/6eb6c781aa9b6438e0c7307bd102788a75fe1a6d/skills/cloudflare/SKILL.md#L157) для этого отдельно указаны закреплённые версии пакетов, установленные типы и схема конфигурации. Если проект использует предыдущую основную версию библиотеки, пример из последней документации может ему не подойти.

Для вашего проекта полезно указать, где искать первоисточник: внутреннюю документацию, репозиторий зависимости или официальный справочник. Если источник недоступен, агент должен сообщить, что не удалось проверить. Правило полезно при работе с меняющимися API; искать в интернете подтверждение каждой простой операции не требуется.

## Keep changes focused on the requested task

_Сохраняйте границы поставленной задачи._

Это адаптация [принципов работы навыка Cloudflare](https://github.com/cloudflare/skills/blob/6eb6c781aa9b6438e0c7307bd102788a75fe1a6d/skills/cloudflare/SKILL.md#L161). Правило сохраняет необходимые для задачи изменения реализации, вызовов, тестов и документации и ограничивает попутную уборку. Выбор границ структурного изменения разобран в [«Рефакторинге»](refactoring.md).

## Make behavior-changing assumptions explicit

_Явно называйте допущения, которые меняют поведение решения._

Это адаптация правила из [AGENTS.md проекта RustFS](https://github.com/rustfs/rustfs/blob/7b010ddd70903028dc5d5d1f00d2356472132403/AGENTS.md#L30), где требуется сообщать допущения, влияющие на поведение или проверку. Если требование не определяет часовой пояс отчёта, агент может молча выбрать UTC. Код и тесты будут согласованы между собой, но пользователи получат отчёт за другие сутки. Правило требует назвать такой выбор и его последствия, чтобы вы могли проверить их до реализации.

Не каждое решение требует вопроса. Агент сначала ищет ответ в требованиях и коде проекта; если ответа нет и ошибка существенно изменит результат, задаёт конкретный вопрос. Выбор имени локальной переменной обычно не требует обсуждения, а границы отчётного дня или поведение при повторном запросе требуют.

## Report what you verified and what you could not verify

_Сообщайте, что проверено и что проверить не удалось._

Это адаптация запрета из [AGENTS.md проекта TransformerLens](https://github.com/TransformerLensOrg/TransformerLens/blob/6bea1fa7cfcbf9064aa8ac99bbd5fb1e4a6c2240/AGENTS.md#L160) заявлять об успешных тестах без их запуска. Фраза «всё работает» не объясняет, запускал ли агент приложение или только прочитал код. Правило требует отчёта с границами проверки: например, тесты расчёта прошли, а отправка письма через реальный сервис не проверена, потому что в окружении нет доступа к нему.

Проверка должна соответствовать изменению. Для правки текста обычно достаточно линтеров и сборки, а изменение формы требует проверки затронутого сценария. Если проверка упала или не запустилась, агент называет причину и оставшийся пробел. Это дополняет [проверяемый результат](give-agent-a-way-to-verify.md): вы видите, на каких свидетельствах основан вывод о готовности.
