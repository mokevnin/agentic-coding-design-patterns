## Candidates worth retaining

| Candidate | Priority / readiness | Why it remains distinct |
| --- | --- | --- |
| `visual-specification` | Strong next chapter | A visual reference is task input; screenshot checking in the feedback-loop chapter is output verification. Show selection of a screen/state, explicit behavioral requirements and visual iteration. Accessibility and responsive behavior need their own criteria. [Image Spec source](https://github.com/PaulDuvall/ai-development-patterns#image-spec). |
| `reviewable-agent-delivery` | Strong next chapter, including cleanup | Human acceptance needs a scoped change, rationale, revision-specific evidence and a feedback loop. Writer/Reviewer concerns independent agent criticism; it does not define this human-facing artifact. Matt Pocock's current [PR skill](https://github.com/mattpocock/skills/blob/main/skills/engineering/pr/SKILL.md) supplies a concrete implementation. Do not use “141 PRs in a day” as evidence of effectiveness. |
| `approved-scenario-fixtures` | Strong next chapter | The reusable unit is a domain-readable input/expectation fixture reviewed by a person, with a separately checked runner. This addresses the cost of reviewing generated tests; it is not just the order of writing tests. The catalog's original domain could not be fetched, but its [author-owned GitHub Pages copy](https://lexler.github.io/augmented-coding-patterns/patterns/approved-scenarios/) was readable. |
| `mutation-guided-test-hardening` | Strong next chapter | Deliberately damaged code tests the detection power of existing assertions. This adds a different external signal from TDD and code review. The [source experiment](https://martinfowler.com/articles/sensors-for-coding-agents.html#MutationTesting) also describes cost and incremental runs; a score does not prove that requirements are correct. |
| `linear-code-walkthrough` | Retain, including interactive explanation | This fills a reader-understanding gap left by verification and review. Keep the chapter focused on one execution path or algorithm and on checking explanations against actual source. |
| `working-example-library` | Retain | A selected working implementation is reusable evidence and material for adaptation, rather than a procedure or a new experiment. Show provenance, assumptions and re-verification when dependencies change. [Source](https://simonwillison.net/guides/agentic-engineering-patterns/hoard-things-you-know-how-to-do/). |
| `evidence-linked-behavior-recovery` | Retain | The result is a validated behavioral contract assembled from complementary artifacts, potentially without complete source. That differs from explaining one code path or refactoring known behavior. Keep the scope to a thin slice; the [experience report](https://martinfowler.com/articles/black-box-to-blueprint.html) does not validate arbitrary whole-system recovery. |
| `bounded-retry-escalation` | Retain | This governs when to stop an unproductive strategy, preserve verified work and change the approach. Neither success verification nor checkpointing makes that decision. Keep progress observable and budgets explicit; the [handbook's numerical retry advice](https://danielmeppiel.github.io/agentic-sdlc-handbook/handbook/ch20-anti-patterns-and-failure-modes.html#cost-runaway) is an example, not a universal threshold. |
| `guided-manual-procedure` | Retain, lower priority | The human performs inaccessible actions while the agent prepares the procedure and captures results. That is a different division of work from automated bootstrap. The current [wizard skill](https://github.com/mattpocock/skills/blob/main/skills/engineering/wizard/SKILL.md) gives a concrete implementation and distinguishes static script checks from completing the human procedure. |
| `held-out-acceptance-scenarios` | Conditional | Independence of acceptance evidence differs from fixture readability. Keep requirements explicit and make read/write boundaries concrete; do not infer a precise access-control design from scenarios merely being outside a repository. [StrongDM's report](https://factory.strongdm.ai/) supports the holdout analogy, not every proposed adaptation or removal of human review. |
| `verified-recovery-points` | Conditional | Context Forking already covers conversation/code alignment and checkpoint limitations. A separate chapter must earn its place through coherent recovery across code, data and external effects while preserving unrelated work. If it only repeats Git checkpoints, merge it into Context Forking. Adapt the [source](https://se-ml.github.io/agentic_patterns/08-rollback-reversibility/); do not reproduce its blanket destructive reset examples. |

Do not combine approved fixtures, held-out acceptance and mutation testing into a generic “better tests” chapter. They address different questions: can a person inspect the expectations, can the implementation influence its acceptance evidence, and do assertions detect deliberately introduced faults?
