## P1 — changes what the reader does

### 1. Auto mode is the default permission mode; both vendors now put a model reviewer at the approval boundary

Recommendation: **update** `executable-guardrails.md` (Implementation step 2 and Known uses) and add first-party evidence to the `approval-fatigue` candidate.

Claude Code sessions in the terminal and in VS Code now start in auto mode when no permission mode is configured, "on every plan and provider". The [changelog for 2.1.284](https://code.claude.com/docs/en/changelog#2-1-284) records this change on 2026-09-28. The [permission-modes page](https://code.claude.com/docs/en/permission-modes#which-mode-a-session-starts-in) gives the threshold as v2.1.283. On earlier versions auto mode was the default only on Pro, Max, Ultra and Team plans; the weekly digest for [2026-w32](https://code.claude.com/docs/en/whats-new/2026-w32) dates that first step to August. In auto mode a separate classifier reviews actions instead of a person. `claude -p` and the Agent SDK still start in Manual mode. `"auto"` in a project's `.claude/settings.json` does not take effect, so a cloned repository cannot opt you into it ([same page](https://code.claude.com/docs/en/permission-modes#eliminate-permission-prompts-with-auto-mode)). `executable-guardrails.md` step 2 still tells the reader to start from manual confirmation of `git push` and network access. A reader on a current install starts somewhere else, and the book never mentions auto mode at all; `grep` finds no occurrence in `book/ru`.

The docs add a line that states the chapter's thesis better than the chapter does: the classifier treats boundaries you state in conversation ("don't push") as block signals, but "boundaries are not stored as rules. The classifier re-reads them from the transcript on each check, so a boundary can be lost if context compaction removes the message that stated it. For a hard guarantee, add a deny rule instead" ([permission modes, boundaries you state in conversation](https://code.claude.com/docs/en/permission-modes#boundaries-you-state-in-conversation)). The living [best-practices page](https://code.claude.com/docs/en/best-practices#deterministic-and-non-deterministic-instructions), last updated around 2026-10-27, now organizes guidance as a two-column table: non-deterministic instructions that Claude decides (prompt, `CLAUDE.md`, auto mode's classifier, `/goal`) versus deterministic ones that Claude Code enforces (hooks, deny rules, sandbox in strict mode, Stop hook, CI, branch protection). That is the chapter's argument in vendor form and worth citing in Known uses. Auto mode pauses and returns to prompting after 3 consecutive or 20 total blocks ([fallback rules](https://code.claude.com/docs/en/permission-modes#when-auto-mode-falls-back)). `/auto-mode-setup` drafts `autoMode.environment` entries from the project and recent sessions for the user to review. The command is older ([commands reference](https://code.claude.com/docs/en/commands), v2.1.228+); [2.1.304](https://code.claude.com/docs/en/changelog#2-1-304) extended it to Bedrock, Vertex, Foundry and telemetry-disabled sessions.

Codex has the same shape. With `approvals_reviewer = "auto_review"` and an interactive approval policy, escalation requests at the sandbox boundary go to a separate reviewer agent instead of a person. The docs stress that this is "a reviewer swap, not a permission grant": it does not widen writable roots or network access ([Auto-review](https://learn.chatgpt.com/docs/sandboxing/auto-review)). In the desktop app the same setting is labelled **Approve for me**. The currency audit's C1 already asks for `approvals_reviewer` in the maintenance chapter; the new point here is that `executable-guardrails` should explain the tier for both tools. Deterministic limits come first, the model reviewer handles the remaining boundary crossings, and explicit ask rules remain for decisions that need a human.

For `approval-fatigue` (currently sourced only to a pattern-encyclopedia entry and the Codex best-practices page), Anthropic's [auto mode engineering post](https://www.anthropic.com/research/claude-code-auto-mode) (2026-03-25, pre-window) gives the missing first-party numbers: "in practice users accept 93% of them anyway", which "leads to approval fatigue". It also states a limit: "The 17% false-negative rate on real overeager actions is the honest number", and the classifier "is not a drop-in replacement for careful human review on high-stakes infrastructure". With both vendors shipping a default that replaces most prompts, this candidate now describes a problem the tools themselves are designed around. Recommend promoting its priority. The candidate could also fold into `executable-guardrails` as a section on where human decisions remain.

### 2. Instructions decay when the model changes; both vendors now ship an audit for it

Recommendation: **update** `scheduled-maintenance.md` (Claude Code `/doctor` subsection, plus a Codex prompt), `bloated-agents-md.md` (Signs / How to do better) and `agent-workflow-evals.md` (Implementation). Propose a **new conditional candidate** (below).

`/doctor prompt-audit` (alias `/checkup prompt-audit`) shipped in [2.1.283](https://code.claude.com/docs/en/changelog#2-1-283) on 2026-09-25. It checks instruction files for "instructions written for older models, references to files or commands that don't exist, and files that contradict each other", and it reports proposed edits without changing anything. By default it covers `CLAUDE.md`, `CLAUDE.local.md` **and `AGENTS.md`**, plus rules, skills, commands, subagents and output styles; a path argument narrows it ([memory docs, audit your instruction files](https://code.claude.com/docs/en/memory#audit-your-instruction-files)). The book's `/doctor` subsection says "for checking AGENTS.md use the `writing-for-agents` pass". That advice is now incomplete: the built-in audit covers `AGENTS.md`, and the monthly instruction pass should name it. The plain `/doctor` checkup also proposes trimming content Claude can derive from the codebase and moving always-loaded guidance into skills and nested files ([skills docs, check your setup](https://code.claude.com/docs/en/skills#check-your-setup-with-/doctor)).

The living [best-practices page](https://code.claude.com/docs/en/best-practices#what-you-can-stop-doing) now has a "What you can stop doing" table. CC-8 covered only its context-window row. The rows relevant here are: drop `IMPORTANT`/ALL CAPS ("piling on emphasis mostly makes Claude over-apply the rule. If it's a rule that can't bend, turn it into a hook or a deny rule"); drop "describe your architecture and file layout in `CLAUDE.md`"; drop "tell Claude to keep going… lines like that are more likely to cause over-work". The page closes with "every one of these was good advice when it was written". The book's current text does not contradict these rows: `bloated-agents-md` already flags architecture retellings, and `agents-md-phrases` uses no emphasis. They still justify a new sign in `bloated-agents-md`: emphasis and "keep going" lines that were written for an older model.

OpenAI says the same in [Rethinking skills and prompts for GPT-6 Astra](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra) (undated). It advises revisiting every `AGENTS.md` instruction with each model release and replacing "Before every edit, read architecture.md…" with contextual pointers. It also notes that instructions written to make an older model run tests or ask first can over-constrain a newer one, and it warns that "Guidance that helps Sol or Luna may overconstrain GPT-6 Astra, so consider which models will use the instructions you leave behind". It closes by suggesting you ask the new model to audit your instructions. [Maintaining software with the GPT-6 family](https://developers.openai.com/blog/maintaining-software-with-the-gpt-6-family) is also undated, but it discusses GPT-6.1 Sol, which became the Codex default in [0.161.0](https://github.com/openai/codex/releases/tag/rust-v0.161.0) on 2026-10-07, so it was written on or after that release. It turns the audit into an experiment: find one `AGENTS.md` instruction that misdirected a past session, replay that session's prompt twice from the same snapshot (instruction unchanged versus removed), and compare quality, tool calls, tokens, runtime and cost. The post also says "future model releases can make these corrections obsolete, so it's important to revisit prompts when new models are released". Superpowers is a concrete case: [v6.4.2](https://github.com/obra/superpowers/releases/tag/v6.4.2) (2026-09-25) rewrote `writing-plans` because "some frontier models, including Opus 5.5, could get overzealous during plan writing" and would start implementing the project.

For `agent-workflow-evals`, the replay is the cheapest possible eval, and the chapter should name a model change as a trigger to rerun the baseline. The chapter's step 5 already records model versions; it does not say "rerun when the model changes". `claude plugin eval` documents this use explicitly (item 4).

Proposed candidate, group `project-org`, slug `model-upgrade-review`: when the default model changes, rerun workflow evals and audit instructions and skills for scaffolding the new model no longer needs (emphasis, step-by-step recipes, "always run tests", "ask before X"), keeping only what still changes behavior in an A/B replay. It differs from `bloated-agents-md` because the trigger is an external model change rather than accumulation, and the remedy is evidence-based removal rather than trimming. Conditional: it may fold into `scheduled-maintenance` as an event-triggered pass, plus a sign in `bloated-agents-md`. Known uses: `/doctor prompt-audit`, the best-practices table, OpenAI's two posts and Superpowers v6.4.2. Anthropic's [harness design post](https://www.anthropic.com/research/harness-design-long-running-apps) (2026-03-24, pre-window) frames the principle: each harness component "encodes an assumption about what the model can't do on its own", and those assumptions are worth re-testing as models improve.

### 3. A project `verify` skill now runs before every commit; `/goal` turns "done" into a checked condition

Recommendation: **update** `give-agent-a-way-to-verify.md`. Add tool blocks in the order AGENTS.md prescribes (agent-independent, then Claude Code, then Codex), since the chapter has none today. Also update the `/run-skill-generator` subsection in `scheduled-maintenance.md`.

Since [2.1.286](https://code.claude.com/docs/en/changelog#2-1-286) (2026-09-30), when a session starts with a skill named `verify` or `simplify` in place, Claude Code's built-in commit instructions tell Claude to run it right before each commit, except for docs-only and tests-only changes ([skills docs, run your checks before each commit](https://code.claude.com/docs/en/skills#run-your-checks-before-each-commit)). Three conditions apply. The skill must load from a project, personal, enterprise or additional-directory location, and the bundled `/verify` and plugin skills don't count. Claude must be able to invoke it, so `disable-model-invocation: true` cancels the behavior. And `includeGitInstructions` must not be turned off. The bundled `/verify` builds and runs the app to confirm a change "without falling back to tests or type checks". When it has no recipe it writes one to `.claude/skills/verify/SKILL.md`, and that recorded project skill then satisfies the commit hook ([run and verify your app](https://code.claude.com/docs/en/skills#run-and-verify-your-app)). For the reader this is a cheap, concrete way to make the feedback loop habitual: commit a `verify` skill once, and every later session runs it before committing. `scheduled-maintenance` currently describes only `/run-skill-generator` and should mention that the recorded recipe feeds `/verify` and the pre-commit run. Caveat: this is still a model-followed instruction, not a git hook, so the deterministic backstop remains CI or a hook.

`/goal` is pre-window (Claude Code [2.1.139](https://code.claude.com/docs/en/changelog#2-1-139); Codex had it by 0.155.0, whose notes include "Block goals after three empty automatic continuation turns", [#44320](https://github.com/openai/codex/releases/tag/rust-v0.155.0)). The verification chapter alludes to it only generically ("tools may support per-session goals, Stop hooks"); the recommendation is to name it concretely, with its limit. In Claude Code a small fast model checks the condition after every turn and returns "not yet met", "met" or "impossible". The evaluator "doesn't run commands or read files independently", so a condition must be something Claude's own output can demonstrate. A good condition has one measurable end state, a stated check (for example "`npm test` exits 0") and constraints such as "no other test file is modified". It may include a stop clause such as "or stop after 20 turns" ([goal docs](https://code.claude.com/docs/en/goal#write-an-effective-condition)). The best-practices table puts `/goal` in the non-deterministic column. That matches the chapter's step 6 (accept work on environment records, not the agent's summary). The right pairing is `/goal` to keep the session working and tests, a Stop hook or CI as the evidence. Codex's `/goal` sets, edits, pauses, resumes and clears a persistent objective of up to 4,000 characters ([developer commands](https://learn.chatgpt.com/docs/developer-commands?surface=cli#set-or-view-a-task-goal-with-goal)). Both tools appear in the OpenAI maintenance post's example prompts (`/goal Look at all recent CI runs to find flaky tests…`).

### 4. `claude plugin eval` is a built-in harness for the workflow-evals chapter

Recommendation: **update** `agent-workflow-evals.md`, adding a Known use and a Claude Code block.

`claude plugin eval` shipped in [2.1.269](https://code.claude.com/docs/en/changelog#2-1-269) on 2026-09-11, a little before the window, and the book never names it ([2026-w37 digest](https://code.claude.com/docs/en/whats-new/2026-w37)). It runs a plugin's suite of cases, each a realistic prompt plus graders (`regex`, `tool_used`, `tool_order`, `file_exists`, LLM-judged rubric, baseline comparison). Each case runs three times by default in a fresh isolated non-interactive session, and the whole suite is repeated with no plugin loaded, so the report shows `WITH`, `W/OUT` and the delta. The docs say: "If a case scores 1.0 both with and without the plugin, the plugin isn't what made it pass." It gates CI on a threshold, and the docs advise pinning `--model` in CI "so a model rollout isn't mistaken for a plugin regression" ([plugin evals](https://code.claude.com/docs/en/plugin-evals#the-no-plugin-baseline)). It accepts a "skills-directory plugin", so a repository's shared skills directory qualifies. `claude plugin eval init` drafts the cases by interviewing you. The chapter's steps (fixtures, trials, baseline, compare candidate on the same fixtures) map almost one-to-one, and the no-plugin arm answers a question the chapter doesn't raise yet: does the skill contribute anything at all? On the Codex side, OpenAI's [Testing Agent Skills Systematically with Evals](https://developers.openai.com/blog/eval-skills) (undated) gives the equivalent recipe (outcome, process, style and efficiency goals; deterministic checks plus rubric; `codex exec --json` traces). It can be cited as the Codex known use.

## P2 — targeted updates

### 5. Hooks can now fail closed

Recommendation: **update** `executable-guardrails.md` step 5 ("check that the mechanism blocks… add input-escaping and timeout checks").

By default a Claude Code hook that fails to start, times out or exits with an unexpected code lets the action through. On `PreToolUse` a timed-out hook "doesn't block the tool call… so don't count on a stalled hook to act as a gate". Since [2.1.295](https://code.claude.com/docs/en/changelog#2-1-295) (2026-10-08), `onFailure: "block"` on command and HTTP hooks blocks the action instead ([hooks reference](https://code.claude.com/docs/en/hooks#block-the-action-when-a-hook-fails)). The docs also warn that "a mistyped path in `settings.json` means the hook never runs". This is the concrete knob behind the chapter's advice to test timeouts: a guardrail hook should be fail-closed, and its first run should be watched. Related, changelog-only (not yet found in the settings reference): [2.1.314](https://code.claude.com/docs/en/changelog#2-1-314) adds `permissions.blockWritesOutsideWorkingDirectories`, which makes Write, Edit and NotebookEdit refuse paths outside the working directories in every permission mode.

### 6. After compaction, only the start of a skill survives

Recommendation: **update** `skills-as-packaged-workflows.md` (Implementation or Consequences).

After auto-compaction, Claude Code re-attaches the most recent invocation of each skill, keeping only "the first 5,000 tokens of each". The re-attached skills share a combined budget of 25,000 tokens, filled from the most recent, "so older skills can be dropped entirely". The troubleshooting advice is to "put the most important instructions near the top of `SKILL.md`" ([skills docs, skill content lifecycle](https://code.claude.com/docs/en/skills#skill-content-lifecycle)). Superpowers [v7.0.1](https://github.com/obra/superpowers/releases/tag/v7.0.1) (2026-10-21) documents a real failure: in one reported session, after a compaction cut off its skill text, `subagent-driven-development` "lost its five-round limit and ran 18 fix rounds on one task". The fix moved the loop, review and resume guidance into `references/` files that are read at the step that needs them, and added a CI test failing any `SKILL.md` at 20,000 bytes. Superpowers measures in characters and bytes; the Claude docs measure in tokens and are authoritative. OpenAI's "Rethinking skills" post gives the same advice from the Codex side: make the root document "a minimal router", and keep descriptions short because with many skills "Codex starts shortening their descriptions to fit". Practical rule for the chapter: put limits and stop conditions first, and move detail into referenced files.

### 7. Instruction-file size limits now truncate silently past a threshold

Recommendation: **update** `bloated-agents-md.md` (Consequences) and possibly `agents-md-memory.md`.

Since [2.1.309](https://code.claude.com/docs/en/changelog#2-1-309) (2026-10-22), an on-demand instruction file over a per-file limit loads only its start, with a note telling Claude to read the rest; "until Claude chooses to, the later instructions aren't in its context". On-demand files are subdirectory `CLAUDE.md`, `.claude/rules` files and path-scoped rules. The limit is 40,000 characters with a 200K window, and 150,000–200,000 characters with 1M depending on model ([memory docs, Claude ignores the end of my subdirectory CLAUDE.md](https://code.claude.com/docs/en/memory#claude-ignores-the-end-of-my-subdirectory-claude-md)). Separately, [2.1.281](https://code.claude.com/docs/en/changelog#2-1-281) made the startup "large CLAUDE.md" notice count instruction files together, so many mid-sized files and `@`-imports also trigger it. The docs keep the 200-line guidance and note that `@` imports "help organization but don't reduce context". This gives the anti-pattern a mechanical consequence besides attention dilution: past the limit, the tail of a file is simply not loaded. The 4 MiB skip and the 200-line guidance may predate the window. Whether the same truncation applies to `AGENTS.md` loaded natively in a subdirectory was not established.

### 8. OpenSpec: `openspec validate --strict` as a pre-commit check

Recommendation: **update** `openspec.md` with one paragraph; the chapter never mentions `validate`.

Releases 1.13–1.16 mostly harden archive, validation and verify. [1.16.0](https://github.com/Fission-AI/OpenSpec/releases/tag/v1.16.0) (2026-10-30) adds a warning for a `Scenario:` with no WHEN/GIVEN or no THEN step, which `--strict` turns into a failure, and makes `validate` exit 1 on an unreadable `config.yaml`. [1.14.3](https://github.com/Fission-AI/OpenSpec/releases/tag/v1.14.3) fixes `validate --all` hanging in pre-commit runners. [1.13.1](https://github.com/Fission-AI/OpenSpec/releases/tag/v1.13.1) adds a `Next:` line to `openspec status` that names the command to resume a change. Together these make `openspec validate --strict` usable as an executable check on spec deltas in a pre-commit hook or CI, which links the OpenSpec chapter to `executable-guardrails`. Everything else in these releases (new tool integrations, `--dry-run`, stores, archive fixes) is below the bar.

### 9. Review rules: Claude Code Review GA with `REVIEW.md`; Codex measured repository rules

Recommendation: **update** `writer-reviewer.md` (Known uses). Optionally add a sentence in the Claude Code review subsection of `scheduled-maintenance.md`.

Claude Code Review (automatic PR review on GitHub, Team and Enterprise) became generally available on 2026-10-15 ([announcement](https://claude.com/resources/articles/code-review-is-now-generally-available)). Review-only instructions go in `REVIEW.md` at the root or in subdirectories. The docs tell you to protect the default branch, because rules are read from the base branch ([customize Code Review](https://code.claude.com/docs/en/code-review-customize)). [2.1.292](https://code.claude.com/docs/en/changelog#2-1-292) made reviews use the base-branch `CLAUDE.md` when a PR edits it, so an author cannot loosen the reviewer's rules in the same PR. That is a neat writer/reviewer detail. **Unverified gap:** the Code Review pages name only `CLAUDE.md` and `REVIEW.md` and say nothing about `AGENTS.md`. Since the book standardizes on `AGENTS.md`, it should not claim that managed Code Review reads it; the documented path is `REVIEW.md`.

On the Codex side, [Custom Code Review rules for Codex](https://developers.openai.com/blog/custom-code-review-rules-for-codex) (undated) reports an eval: "rule-guided variants recovered 98% of the required custom findings, compared with 58.3% in the baseline control". It recommends repository-wide rules at the root and service rules in their directory, and links the real rule in the Codex repository's `AGENTS.md`. The book already names `## Code Review Rules` in `scheduled-maintenance.md`, so this is evidence for that advice, and for the `feedback-flywheel` candidate: a comment that keeps coming back becomes a scoped rule.

### 10. Codex `/import` moves a Claude Code setup, including private memories, into Codex

Recommendation: **update** `agents-md-memory.md` (Codex block, one sentence), and treat this mainly as evidence for `private-agent-memory`.

[Import from another agent](https://learn.chatgpt.com/docs/import) brings instructions, `settings.json`, skills, plugins, MCP servers, hooks, slash commands (as skills), subagents and recent chats from Claude Code or Cursor into Codex. Instruction files go to `AGENTS.md`, and "project memories from Claude Code" go to Codex Memories. The CLI imports up to 50 chats from the last 30 days. [0.165.0](https://github.com/openai/codex/releases/tag/rust-v0.165.0) (2026-10-27) extended imports to the new memory store ([#56414](https://github.com/openai/codex/pull/56414)). The introduction date of `/import` itself was not established; it was already available locally by 0.157.0 (2026-09-25). For `private-agent-memory` this is a strong new argument. Vendor-side private memory now migrates between tools, but it still never passes through the repository or review, so a team member's private Claude memory can become their private Codex memory.

Do not report the same release's "Enabled memory v2 by default for fresh profiles" as "memories are on by default". [PR #56211](https://github.com/openai/codex/pull/56211) selects the v2 *format* "when memories are enabled and the `memories` directory is absent". The [Memories docs](https://learn.chatgpt.com/docs/customization/memories) still say "Local Codex memories are off by default", so the book's current claim stands.

## Second opinion (Codex CLI 0.166.0, 2026-10-31)

An independent read-only review by Codex checked this note against primary sources and the targeted Russian chapters. Corrections to apply before acting on the findings above:

- **Item 1:** Codex's [documented approval default](https://learn.chatgpt.com/docs/agent-approvals-security) is still `"user"`; `auto_review` is opt-in. Do not write that both vendors default to a model reviewer. Approval fatigue is already in the problem and anti-patterns of `executable-guardrails`, so the addition is the probabilistic reviewer tier, not the fatigue argument.
- **Item 2:** `bloated-agents-md` already says to remove instructions that change nothing. Add `/doctor prompt-audit` to `scheduled-maintenance` and a model-change trigger to `agent-workflow-evals`; skip the `model-upgrade-review` candidate. Codex's suggested audit prompt is not a built-in command.
- **Item 3:** `scheduled-maintenance` already connects `/run-skill-generator` to `/run` and `/verify`; only the commit-time behavior is missing. "Runs before every commit" is too categorical: these are model-followed instructions with exceptions.
- **Item 4:** add pinning the judge model, bounded cost, `--no-publish` for local reports, and that a positive ablation delta does not gate the exit status ([plugin evals](https://code.claude.com/docs/en/plugin-evals)).
- **Item 5:** `onFailure: "block"` has no effect on Stop-family and background command hooks ([hooks](https://code.claude.com/docs/en/hooks#block-the-action-when-a-hook-fails)).
- **Item 7:** "truncate silently" is misleading: the loaded prefix ends with an explicit notice telling Claude to read the rest ([memory](https://code.claude.com/docs/en/memory#claude-ignores-the-end-of-my-subdirectory-claude-md)).
- **Item 8:** `openspec validate --strict` without a selector opens an interactive picker and exits 1 non-interactively. Use `openspec validate --all --strict --no-interactive` ([source](https://github.com/Fission-AI/OpenSpec/blob/v1.16.0/src/commands/validate.ts)).
- **Item 9:** managed Claude Code Review reads `REVIEW.md`; local `/code-review` does not ([customization](https://code.claude.com/docs/en/code-review-customize)).
- **Item 10:** memory import in `/import` sits behind `external_agent_memory_import`, which is "under development" and off in 0.166.0 (`codex features list`). The docs also conflict with [0.157](https://github.com/openai/codex/releases/tag/rust-v0.157.0) on daemon/remote sessions.
- **Missed:** in [0.163](https://github.com/openai/codex/releases/tag/rust-v0.163.0), interrupting also stops active Code Mode cells and nested calls, which matters for supervision. No missed feature warrants a new chapter.

Codex's suggested order: fail-closed hooks and the approval-reviewer boundary; a plugin-eval example with ablation and judge pinning; compaction loss and scoped truncation; the model-upgrade audit trigger, `/verify`, the corrected OpenSpec command; short known uses for review rules and managed worktrees.
